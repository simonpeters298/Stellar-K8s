## Overview

This document covers four cohesive platform engineering changes implemented as a unified wave.
They share a common architectural spine: every scaling decision, scheduling action, and
admission verdict flows through the tamper-evident audit chain (Epic #1479), and every
image admitted must carry verifiable supply-chain provenance (Epic #1477).

`
CI Build (GitHub Actions)
   |-> Container Image + SLSA Provenance Attestation (Epic #1477)
   |-> OCI Referrer Graph (Cosign signature + SBOM)
               |
               v
   Admission Webhook
   |-> Verify provenance (Epic #1477)    --> AuditChain log (Epic #1479)
   |-> Check tenant quota (Epic #1480)   --> AuditChain log (Epic #1479)
   |-> Adaptive HPA trigger (Epic #1478) --> AuditChain log (Epic #1479)
               |
               v
   Fair-Share Scheduler Extension (Epic #1480)
   |-> DRF share calculation
   |-> Jain Fairness Index enforcement
`

## Epic #1477 — End-to-End Supply-Chain Provenance Attestation

### Architecture

Every build artefact (container image, Helm chart, binary) now carries an
in-toto/SLSA v1.0 provenance attestation attached to the OCI Referrer Graph.
The admission webhook verifies the attestation before allowing any Pod to start.

### Components

| Component | Location |
|-----------|----------|
| Provenance core library | src/provenance.rs |
| CI workflow | .github/workflows/supply-chain-provenance.yml |
| Helm values | charts/stellar-operator/vvalues.yaml — provenance.* |
| Kyverno policies | policy/kyverno-policies.yaml — 
equire-image-provenance, 
equire-image-digest-pin |

### CI Pipeline (5 Jobs)

1. **build** — Builds or reuses the existing sha-<SHA> image from GHCR
2. **sbom** — Generates CycloneDX SBOM with nchore/sbom-action
3. **attest** — Creates SLSA v1.0 GitHub-hosted attestation (ctions/attest-build-provenance@v4)
4. **sign** — Keyless Cosign signing via OIDC token; entry added to Rekor
5. **verify** — End-to-end gate: gh attestation verify + cosign verify

### Admission Gate

Configure in values.yaml:

`yaml
provenance:
  enabled: true
  minimumSlsaLevel: L2   # L1 | L2 | L3
  trustedRegistries:
    - "ghcr.io/otoworg/*"
  failurePolicy: Deny    # Deny | Warn | Audit
  oidcIssuer: "https://token.actions.githubusercontent.com"
`

### Provenance Verification (Rust API)

`
ust
use stellar_k8s::provenance::{ProvenanceVerifier, ProvenanceVerificationPolicy, SlsaLevel};

let policy = ProvenanceVerificationPolicy {
    minimum_slsa_level: SlsaLevel::L2,
    trusted_registries: vec!["ghcr.io/otoworg/*".into()],
    require_signed: true,
    ..Default::default()
};
let verifier = ProvenanceVerifier::new(policy);
verifier.verify_statement(&statement, "sha256:abc...")?;
`

## Epic #1479 — Immutable Audit Event Pipeline with Tamper-Evident Chain Hashing

### Architecture

All operator events (admission decisions, config changes, quota overrides, scaling
actions) are appended to a cryptographically linked hash chain. Each record is:

`
H_n = SHA256(H_{n-1} || seq_n || timestamp_n || event_json_n)
`

Genesis: H_0 = SHA256("STELLAR_K8S_AUDIT_GENESIS_v1:" || cluster_id)

Periodic signed Merkle checkpoints prevent log truncation attacks.

### Components

| Component | Location |
|-----------|----------|
| Audit chain core | src/audit_chain.rs |
| Helm values | charts/stellar-operator/vvalues.yaml — uditChain.* |
| Kyverno protection | policy/kyverno-policies.yaml — protect-audit-chain-configmap |

### Configuration

`yaml
auditChain:
  enabled: true
  backend: configmap       # memory | configmap | postgres
  maxInMemoryRecords: 1000
  checkpointInterval: "15m"
  signingKeySecretRef:
    name: "stellar-audit-hmac-key"
    key: "key"
  siemExport:
    enabled: true
    endpoint: "https://your-siem/ingest"
    batchSize: 100
`

### Rust API

`
ust
use stellar_k8s::audit_chain::{AuditChain, AuditEvent, AuditEventType};

let mut chain = AuditChain::new("my-cluster".to_string(), Some(signing_key));

chain.append(AuditEvent {
    event_type: AuditEventType::AdmissionDecision,
    actor: "webhook".to_string(),
    resource: "pod/my-pod".to_string(),
    action: "admit".to_string(),
    outcome: "allowed".to_string(),
    ..Default::default()
});

// Verify chain integrity
let result = chain.verify();
assert!(result.is_ok(), "Chain has been tampered with!");

// Create a signed Merkle checkpoint
let checkpoint = chain.create_checkpoint()?;
`

## Epic #1478 — Adaptive Horizontal Pod Autoscaling on Custom Business SLIs

### Architecture

The Adaptive HPA controller replaces static HPA metrics with six Stellar-specific
business SLIs. EWMA smoothing prevents oscillation; asymmetric hysteresis (fast
scale-up, 300s scale-down window) prevents thrashing.

### Monitored SLIs

| SLI | Target | Source |
|-----|--------|--------|
| LedgerCloseLatencyMillis | p95 < 5,000 ms | Stellar Core /metrics |
| LedgerSyncLag | ≤ 1 ledger behind | Stellar Core /info |
| HorizonTxQueueDepth | ≤ 200 queued | Horizon /metrics |
| SorobanInvocationLatency | p95 < 300 ms | Soroban RPC |
| FeeStatCongestionRatio | < 0.85 | Fee-stats API |
| TransactionThroughputTps | 100 TPS/replica | Horizon /metrics |

### Scaling Algorithm

1. Collect SLI measurements from Prometheus endpoint
2. Apply EWMA smoothing: E_t = α × raw + (1 − α) × E_{t-1}
3. Compute per-SLI pressure: pressure = observed / target
4. Take max(pressure) across all SLIs → dominant pressure
5. Compute desired_replicas = ceil(current × dominant_pressure)
6. Clamp to [minReplicas, maxReplicas]
7. Apply scale-down stabilisation window (default 300s)
8. Check monthly cost cap before scale-up

### Components

| Component | Location |
|-----------|----------|
| HPA engine | src/adaptive_hpa.rs |
| Existing CRD | src/crd/stellar_autoscaler.rs |
| Helm values | charts/stellar-operator/vvalues.yaml — daptiveHpa.* |

### Configuration

`yaml

  enabled: true
  ewmaAlpha: 0.3
  scaleDownStabilizationWindowSeconds: 300
  maxReplicas: 50
  minReplicas: 1
  monthlyCostCapUsd: 500
  prometheusEndpoint: "http://prometheus-operated:9090"
  sliTargets:
    ledgerCloseLatencyMs: 5000
    horizonTxQueueDepth: 200
    sorobanInvocationLatencyMs: 300
`

## Epic #1480 — Declarative Multi-Tenant Quota & Fair-Share Scheduler Extension

### Architecture

Implements Dominant Resource Fairness (DRF) scheduling. Each tenant is assigned a
weighted dominant share D_t = max(s_cpu, s_mem) / weight_t. Pods from tenants
with the lowest D_t are admitted first. The admission webhook enforces hard quota
limits before scheduling.

### Fairness Guarantee

**Jain's Fairness Index** is tracked continuously. An alert fires when JFI drops
below the configured threshold (default 0.90):

`
J = (Σ x_i)² / (n × Σ x_i²)
`

Perfect fairness → J = 1.0; Maximum unfairness (one tenant takes all) → J = 1/n.
